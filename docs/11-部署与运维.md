# 11：部署与运维

## 概念

“电脑上能跑”不等于“可以上线”。生产部署需要同时考虑密钥、HTTPS、数据库和文件备份、日志、恢复演练、资源容量，以及 Worker 和模型供应商故障时能否定位。KnowFlow 的 Docker Compose 是可靠的单机起点；公网生产环境还需反向代理、域名、TLS 和私有存储方案。

## 本阶段目标

能安全地区分开发/生产配置；会做并验证本地备份；理解 Docker Compose 在生产中的职责边界。

## 上线前配置清单

生产 `.env` 至少应满足：

```dotenv
DEBUG=false
SECRET_KEY=高强度随机值且仅存于密钥管理系统
ALLOWED_HOSTS=你的域名.example.com
DEEPSEEK_API_KEY=生产环境独立Key
SILICONFLOW_API_KEY=生产环境独立Key
```

原则：

1. 不将 `.env`、Key、数据库密码提交 Git。
2. 数据库和 Redis 不映射到公网端口；只允许 Web/Worker 内网访问。
3. 开放给用户的只有 HTTPS 443（HTTP 80 仅用于跳转或证书校验）。
4. 生产数据库密码与本地默认密码不同，模型 Key 也应和开发环境分开。
5. 上传文件不要由未经鉴权的公开静态目录直接暴露。

## 推荐部署拓扑

```text
浏览器 ─HTTPS→ Nginx / 云负载均衡
                       │ HTTP + WebSocket
                       ▼
                 KnowFlow web（Daphne）
                    │         │
           PostgreSQL/pgvector Redis ←→ Celery Worker
                    │
              私有媒体卷 / 对象存储
```

Nginx 代理 WebSocket 时必须保留升级头：

```nginx
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_set_header Host $host;
```

若缺少前两行，普通页面可能正常，但实时进度和流式回答会失败。TLS 可使用 Certbot 或云负载均衡器终止；无论哪种，都要验证 `/ws/...` 在 HTTPS 下使用 `wss://`。

## 操作步骤：本地备份

项目使用 PostgreSQL，不是 SQLite。备份脚本会导出数据库、复制 Docker 媒体卷，生成按日期命名的 ZIP，并清理超期备份：

```powershell
cd D:\python\KnowFlow
.\scripts\backup.ps1
```

常用参数：

```powershell
.\scripts\backup.ps1 -RetentionDays 30
.\scripts\backup.ps1 -OutputDirectory D:\backups
```

备份包包含 `postgres.sql` 和 `media/`。运行后不要只看“脚本完成”，请打开 ZIP，确认两个内容都在，并记录备份时间、大小和保存位置。

## 恢复演练（必须在可丢弃环境进行）

恢复演练比“有备份”更重要。不要在唯一生产数据上练习。

1. 准备一台空 Docker 环境或先明确备份现有数据。
2. 启动 `db` 服务，等待 healthy。
3. 将备份中的 `postgres.sql` 导入对应 PostgreSQL 数据库。
4. 将 `media/` 内容恢复到 `media_data` 卷。
5. 启动 Web 与 Worker。
6. 登录验证组织、知识库、文档数量、已就绪文档、切片数量和问答来源。
7. 记录恢复耗时和发现的问题。

数据库恢复了但媒体卷丢失，下载原文件和重传版本都会异常；媒体卷恢复了但数据库丢失，文件也没有归属和权限。因此两者必须成对备份。

## 日常观察与故障定位

| 目标 | 命令/位置 | 关注点 |
| --- | --- | --- |
| 容器健康 | `docker compose ps` | Web/Worker 是否 running，db/redis 是否 healthy |
| Web 报错 | `docker compose logs -f web` | 500、路由、数据库连接、ASGI 错误 |
| 异步任务 | `docker compose logs -f worker` | Provider 失败、重试、解析异常 |
| 业务证据 | 任务详情、审计日志、用量页 | 某次操作谁执行、何时失败 |
| 数据一致性 | Django Admin / 只读 shell | 文档版本、Chunk、任务状态是否匹配 |

发生问题时先保存日志和时间点，再改变配置。盲目重建容器或删除卷通常会让原始证据和数据一起消失。

## 编码任务

完成一次恢复演练报告，至少记录：备份文件名、备份日期、恢复环境、恢复步骤、恢复耗时、知识库/文档/Chunk 数量核对结果，以及遇到的错误和改进项。将报告与备份策略一起写入团队 Wiki 或项目文档。

## 验收清单

- [ ] 生产配置使用 `DEBUG=false`、强 `SECRET_KEY` 与严格 `ALLOWED_HOSTS`。
- [ ] PostgreSQL、Redis 不对公网暴露。
- [ ] HTTPS 与 WebSocket 均能通过反向代理访问。
- [ ] 已生成数据库 + 媒体文件的可打开备份包。
- [ ] 已至少做过一次在空环境中的恢复演练。
- [ ] Worker/API 故障能从任务记录和日志定位。

## 常见错误

| 错误 | 后果 | 修正 |
| --- | --- | --- |
| 生产仍 `DEBUG=true` | 暴露调试信息与配置 | 上线前禁用并做错误页测试 |
| 只备份数据库 | 上传原文件和版本不可恢复 | 同时备份 `media_data` |
| 备份从未恢复验证 | 真出事故才发现不可用 | 定期恢复演练 |
| Redis/PG 映射公网端口 | 被扫描、爆破或破坏 | 仅内网暴露，设访问控制 |
| Nginx 未配置 Upgrade | WebSocket 断开 | 加升级头并用浏览器验证 |
