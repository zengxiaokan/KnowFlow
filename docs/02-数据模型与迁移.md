# 02：数据模型与迁移

## 概念

KnowFlow 的第一条数据原则是：**Organization 是租户边界**。知识库、文档、会话、模型用量、任务、工作流运行和审计日志都能沿外键追溯到组织。任何查询都必须先限定组织范围，才能防止“猜一个 URL ID 就读到别人的资料”。

第二条原则是：**稳定对象与可变版本分开**。`Document` 表示一份业务资料，`DocumentVersion` 表示第几次上传。只有新版本切片和向量都写入成功后，`Document.current_version` 才会切换，所以失败的重传不会破坏旧资料的问答与历史引用。

## 本阶段目标

读懂主要实体关系；能给模型添加字段并生成、执行、验证迁移；知道为什么不能手改数据库代替迁移。

## 核心实体关系

```text
User ──< Membership >── Organization
                         ├──< KnowledgeBase ──< Document ──< DocumentVersion ──< Chunk
                         │        └──< KnowledgeBaseMembership >── User
                         ├──< Conversation ──< Message >──< Chunk（引用来源）
                         ├──< ModelUsageRecord / IngestionTask / AuditLog
                         └──< Workflow ──< WorkflowVersion ──< WorkflowRun ──< WorkflowStepRun
```

| 模型 | 作用 | 重点 |
| --- | --- | --- |
| `Organization` / `Membership` | 多租户与组织角色 | 注册自动建个人组织；角色为 owner/editor/viewer |
| `KnowledgeBase` | 可检索资料集合 | 可组织内可见或仅授权成员；可有助手规则 |
| `Document` / `DocumentVersion` | 文档与上传版本 | 只让 `current_version` 参与检索 |
| `IngestionTask` | 面向用户的任务状态 | 保存阶段、进度、尝试次数、错误码 |
| `Chunk` | 检索基本单位 | 标题、正文、序号和 1024 维向量 |
| `Conversation` / `Message` | 会话、回答、引用 | 助手消息有 generating/complete/failed 状态 |
| `Workflow*` | 可追溯自动化 | 运行固定指向一个 WorkflowVersion |

## 操作步骤

### 1. 先读模型

依次阅读 `apps/identity/models.py`、`apps/knowledge/models.py`、`apps/chat/models.py`、`apps/workflows/models.py`。特别看 `ForeignKey(..., on_delete=...)`：删除文档会级联删除版本、任务和切片；删除知识库会级联删除其文档与会话。业务服务会在事务提交后另外删除对应媒体文件。

`Chunk.embedding` 是 pgvector 的 1024 维 `VectorField`，并建有余弦距离 HNSW 索引。Embedding 模型维度改变时不能只改 `.env`；必须重新向量化并重建相容索引。

### 2. 查看迁移

```powershell
docker compose exec web python manage.py showmigrations
docker compose exec web python manage.py sqlmigrate knowledge 0001
```

`[X]` 表示迁移已应用。`sqlmigrate` 只打印 SQL，不会改数据库，是理解 ORM 如何创建列、约束与索引的安全方式。

### 3. 练习添加字段

给 `KnowledgeBase` 添加可选 `icon`：

```python
icon = models.CharField(max_length=32, blank=True)
```

然后执行：

```powershell
docker compose exec web python manage.py makemigrations knowledge
docker compose exec web python manage.py migrate
```

打开新生成的迁移文件，确认它只包含预期的 `AddField`。之后再让表单、模板或 Admin 实际读写这个字段；仅有数据库列不算完成需求。已共享或部署过的迁移绝不能修改，应新建下一条迁移。

## 编码任务

给 `DocumentVersion` 增加 `parser_version` 元数据：说明它何时写入、为什么属于版本而不是文档；生成迁移；解析成功后写入；在详情或 Admin 展示；测试重传后的版本 1、2 可以有不同值。

## 验收清单

- [ ] 新用户有一个个人组织和 owner 身份。
- [ ] 能画出 `Document → DocumentVersion → Chunk`。
- [ ] 知道为何不能在上传时立刻切换 `current_version`。
- [ ] 新迁移在 `showmigrations` 中为 `[X]`。
- [ ] 不同组织账号无法通过页面、API 或 URL 读取对方资料。

## 常见错误

| 错误 | 后果 | 修正 |
| --- | --- | --- |
| 改模型不建迁移 | 代码和数据库结构不一致 | `makemigrations` 并提交迁移文件 |
| 手工给数据库加列 | 其他环境无法复现 | 用 Django migration 记录所有结构变化 |
| 上传即覆盖当前版本 | 新版失败后旧资料不可用 | 只在完整索引成功后切换 |
| 仅按 `pk` 查询 | 可猜 ID 越权 | 从 `visible_knowledge_bases(user)` 开始 |
| 混用不同维度向量 | 入库或检索失效 | 模型换代时重新索引 |
