# 09：任务编排与幂等性

## 概念

分布式任务系统不能承诺“同一消息只会执行一次”。Worker 可能在写完部分数据后崩溃，消息确认可能丢失，网络超时后客户端也可能再次投递。因此需要**幂等性**：同一个任务重复执行一次或多次，最终业务结果仍正确，不会出现重复 Chunk、重复扣费记录或不可解释的工作流结果。

不要把幂等性理解成“代码从不重复运行”。它的真正含义是“即使重复运行，最终状态也可预测”。

## 本阶段目标

知道文档处理和工作流分别如何避免重复污染；会人工观察一次安全重试；能在修改异步代码时确定正确的事务边界。

## 文档任务如何保持安全

`process_document()` 开始时会先判断：如果 `IngestionTask.status == succeeded`，直接返回，不会再次写入。正常流程中：

1. 解析、切片、请求向量均在数据库事务外进行，避免长时间锁表。
2. 到“索引”阶段才进入 `transaction.atomic()`。
3. 先删除 **同一 DocumentVersion** 已存在的 Chunk。
4. 使用 `bulk_create()` 写入这一版本所有 Chunk。
5. 同一事务更新 `document.current_version` 与文档 `ready` 状态。

`Chunk(document_version, ordinal)` 还有唯一约束，是数据库层最后一道保护。服务层逻辑和数据库约束应同时存在，不能只依赖其中一个。

> 说明：Embedding Provider 调用在重试时仍可能发生多次，外部供应商通常无法被本地数据库完全“精确一次”控制。系统追求的是业务数据不重复、错误可见、用量可审计。

## 工作流如何保持可解释

工作流运行不修改其 `WorkflowVersion.definition`。`WorkflowRun` 一创建就固定关联某个已发布版本，输入保存到 `input_data`；Worker 按定义创建 `WorkflowStepRun`，每一步保存输入、输出、时间和状态。

失败重试不新建一份看不懂的运行记录，而是：

1. 删除该 `WorkflowRun` 的旧 StepRun；
2. 清空 `output_data`、错误与时间；
3. 改回 pending；
4. 再投递同一个 Run。

这样运行 URL 与审计目标保持稳定，重试前后的证据也集中在一个业务运行记录上。

## 操作步骤

### 1. 查看事务边界

打开 `apps/knowledge/tasks.py`，找到：

```python
with transaction.atomic():
    Chunk.objects.filter(document_version=version).delete()
    Chunk.objects.bulk_create(...)
    document.current_version = version
    document.status = Document.Status.READY
    document.save(...)
```

思考如果 `bulk_create` 失败会怎样：事务回滚，旧的切片和 `current_version` 都不会被半更新。再读 `apps/workflows/services.py` 的 `retry_workflow()`，确认它也用事务把“删步骤、清状态、投递新任务”组织起来。

### 2. 用测试验证，而不是手改生产数据

现有测试覆盖切片、生命周期和工作流服务。执行：

```powershell
docker compose exec web pytest -q
```

如果你要新增“重复投递”的回归测试，优先 mock Provider 或使用 demo Provider，避免测试真实扣费。断言应关注结果数量和关联关系，而不是只断言“函数被调用了一次”。

### 3. 推荐的幂等键思路

当将来新增导出、邮件、第三方写入时，先问：重复调用会产生什么副作用？可用的保护包括：

- 数据库唯一约束；
- 业务 ID/请求 ID 作为幂等键；
- 状态机只允许合法状态迁移；
- 事务提交后投递；
- 外部 API 支持时传递对方的 idempotency key；
- 审计日志记录“请求过”与“完成了”两个事实。

分布式锁不是第一选择。它增加超时、续租和故障恢复复杂度，只有唯一约束和状态机不能满足时再考虑。

为“重复执行文档任务”写一个测试：创建含一个版本的任务，使用 fake Embedding Provider；连续调用处理逻辑两次；断言当前版本的 Chunk 数量等于预期，不是两倍，并断言任务最终为 succeeded。再写一个测试验证 `succeeded` 任务再次进入函数时直接返回。

## 验收清单

- [ ] 能指出文档索引事务的起止位置。
- [ ] 重复成功任务不会写入重复 Chunk。
- [ ] 自动重试保留同一 IngestionTask 及其错误历史字段。
- [ ] 每个工作流运行可定位到具体 WorkflowVersion。
- [ ] 工作流失败重试后没有残留旧的 StepRun。

## 常见错误

| 错误做法 | 后果 | 正确方式 |
| --- | --- | --- |
| 认为队列绝不重复投递 | 重启/超时后产生重复数据 | 假设至少一次，设计幂等写入 |
| 先删旧 Chunk，再在事务外慢慢插入 | 中途异常会使资料暂时消失 | 删除、写入、切换版本放在同一事务 |
| 用页面禁用按钮代替幂等 | API、重试、并发仍会重复 | 用状态机、唯一约束和服务层校验 |
| 重试时新建 Run 却不留关联 | 审计和问题排查困难 | 保留运行或明确建立 retry 关联 |
